# VulnLoom 产品定位反方评审

状态：`SELF_GRILL_COMPLETE_WITH_USER_AMENDMENT`

日期：`2026-09-08`

评审对象：`PRODUCT-ARCHITECTURE-ROADMAP.md` 版本 `0.1`

## 1. 结论

原设计选择“一个平台、共享控制面、多个独立引擎”是正确的，但产品定位仍然过宽，四入口缺少主次，
“自主”“红队”“生产安全”和“验证完成”缺少可测试定义。若直接按原文开发，项目可能再次被局部技术里程碑
带偏，或变成工具很多、用户闭环很弱的安全平台。

本轮评审及用户定稿采用以下修正：

- 将产品收敛为面向组织自有或受托软件与网络目标的证据优先自主漏洞研究和攻击验证平台；
- 将源码漏洞研究与授权红队攻击模拟确定为两条主要能力线；
- 将上线前安全验收与生产定期巡检确定为复用核心能力的工程化交付工作流；
- 建立多模型 Provider Center，避免产品被首个 CUC/DeepSeek 接入绑死；
- 用 A0-A4 自治等级代替模糊的“Autonomous”；
- 强制每次报告同时输出 Coverage Ledger、Finding 和未解决 Candidate；
- 将外部 Web 攻击链限定为首个红队边界，暂不隐含完整内网 BAS 能力；
- 增加公开能力声明门禁和阶段性产品发布点。

经过这些修正，四入口可以共存于一个项目，并能用共享领域对象连接。主要剩余风险是路线体量、生产环境
测试策略、Browser/Proxy实现、Raw Evidence保留和许可证，这些必须在对应里程碑前通过 ADR 决定。

## 2. 逐项拷打

### Q1：一句话究竟卖什么？

**攻击意见：** “自动漏洞研究和渗透测试平台”范围过大，无法判断主要客户、主要目标和区别于扫描器的价值。

**决定：** 产品定位为“面向组织自有或受托软件与网络目标的证据优先自主漏洞研究和攻击验证平台”。输入可以是
源码或网络目标，输出必须是覆盖账本、可复测 Finding 和剩余不确定性。

### Q2：四个入口是否意味着四个产品？

**攻击意见：** 源码研究、上线验收、生产巡检和红队的购买者、风险和工具不同，平级建设会耗散团队。

**决定：** 它们共用 Engagement、Scope、Flow、Broker、Evidence、Finding 和 Report，但不平均建设。Source
Hunt 与 Authorized Red Team 是两条主要能力线；上线前验收和生产巡检是组合、约束并调度核心能力的任务模板。
红队能力按影响等级逐段准入，不因其高影响而降为附属路线。

### Q3：比赛能力是否会绑架产品？

**攻击意见：** AIxCC、CTF和真实Web服务的输入、评价标准和执行环境不同；追逐榜单可能再次偏离真实业务。

**决定：** `benchmark` 是 ExecutionProfile 和评测环境，不是产品主入口。比赛用于测量推理、工具和长任务能力，
不能决定生产工作流。Source Hunt的PoV/Fuzz能力可以进入产品，但比赛专用基础设施保持adapter化。

### Q4：凭什么不是“LLM + 扫描器包装”？

**攻击意见：** 只要Agent依次调用Subfinder、Nmap、Nuclei、SQLMap，也可以被包装成自主渗透。

**决定：** 产品级Agent至少必须：

1. 从Observation中形成新的可测试假设；
2. 根据结果修改后续计划；
3. 为Candidate选择最小验证实验；
4. 将相反证据交给独立Critic；
5. 输出覆盖缺口和未解决问题；
6. 在同一预算下避免无意义工具堆叠。

Scanner命中只能成为Signal或Candidate。

### Q5：“自主”到底自主到什么程度？

**攻击意见：** 当前模型建议和固定双工具Session被称作Agent，会造成严重能力错觉。

**决定：** 使用A0-A4自治等级。三个日常入口至少达到A3才可对外称为自主；红队达到A4后才能称为自主攻击
模拟。每个版本公开其最大连续轮数、工具预算、等待审批和恢复能力。

### Q6：生产安全和真实漏洞验证是否冲突？

**攻击意见：** 如果生产环境永远只读，很多漏洞无法证明；如果允许利用，又可能影响业务。

**决定：** `production_safe` 输出可以包含经过低影响差异证明的Finding和需要预发布复现的Candidate。
高影响验证默认转移到镜像环境、预发布环境或单独批准的窗口。报告明确标注证据强度，不能为了“零风险”伪造
已验证结论，也不能为了“验证完整”默认修改生产数据。

### Q7：用户输入授权声明就足够吗？

**攻击意见：** 产品无法仅凭自然语言判断操作者是否真正拥有目标。

**决定：** Control Plane要求操作员身份、authority reference、Scope审批和审计。部署方可以增加域名验证、组织
资产导入和RBAC。技术验证不能替代法律授权，但系统必须阻止Agent自行扩展目标，所有主动动作可追溯到授权对象。

### Q8：资产发现会不会滑向全网扫描？

**攻击意见：** 从域名发现子域、IP和第三方服务时，很容易把相关性误当作授权。

**决定：** 新发现先进入DiscoveredAsset。只有精确命中已批准域名通配、CIDR和端口规则，才成为AuthorizedAsset。
关联SaaS、CDN共享地址、供应商域名和越界重定向只记录，不主动测试。

### Q9：没有账号如何测试认证和密码找回？

**攻击意见：** 无账号黑盒可能诱导Agent操作真实用户，或只能做表面检查。

**决定：** 匿名任务可发现认证面、用户枚举和公开流程。需要状态变化时，只允许自注册身份、控制方拥有的
邮箱/手机号或预置测试身份，并通过Approval。不得对真实第三方身份重置密码、撞库或接管。

### Q10：未启用MFA是不是漏洞？

**攻击意见：** 把最佳实践缺失统一报成漏洞会造成大量低质量Finding。

**决定：** MFA缺失必须结合业务风险、角色、合规要求和安全不变量；MFA绕过则需要动态证据。报告区分
Finding、Hardening Recommendation和Coverage Gap。

### Q11：红队范围是否无限扩张？

**攻击意见：** “红队”可能被理解为钓鱼、终端控制、AD、云、横向移动、持久化和数据外传的全部能力。

**决定：** 首个Red Team产品边界是外部Web/API攻击链，从Recon到受控初始访问与授权后的有限目标达成。
内网、AD、云控制面、社工、持久化和真实外传分别需要独立Threat Model、Runner和ADR，不能由名称自动包含。

### Q12：多Agent是否必要？

**攻击意见：** 为模仿参考项目创建十几个Agent，会增加成本、上下文丢失和调试难度。

**决定：** 角色表示工具和上下文权限，不代表必须启动独立模型会话。首期最多使用Planner、Recon、Web/Source、
Validator、Critic和Reporter。只有隔离上下文或并行收益被Benchmark证明时才拆分会话。

### Q13：单仓库会不会太重？

**攻击意见：** Source、Web、Fuzz、Browser、Scheduler和UI全部放在一起可能形成巨型单体。

**决定：** 采用模块化单仓库和逻辑单体，Engine只通过版本化领域协议交换数据。Runner和高依赖工具使用独立镜像。
当独立扩缩容、语言运行时、许可证或隔离网络形成真实边界时再拆部署，不用微服务制造早期复杂度。

### Q14：前期投入会不会形成沉没成本绑架？

**攻击意见：** “全部保留”可能迫使新Flow绕过大量只为旧Pilot设计的对象。

**决定：** 按安全价值和协议适配成本复用，不按代码量复用。Scope、Policy、Broker、Runner、Evidence、Critic、
Finding和Report优先保留；固定Recommendation、双工具Session和多层人工Intake可成为兼容fixture、可选策略或删除
候选。任何旧抽象若让真实URL纵切增加重复状态，都应通过ADR替换。

### Q15：什么证据才足以成为Finding？

**攻击意见：** 不同漏洞无法用同一个“HTTP 200”规则判断，业务逻辑更没有统一Payload。

**决定：** 建立按漏洞类别版本化的Evidence Requirement。每类定义前置状态、基线、变异请求、可观察差异、
负向控制、影响证明、清理和复测。通用状态机保持一致，类别Judge通过受信任adapter实现。

### Q16：定期巡检与普通扫描器有什么不同？

**攻击意见：** 如果只是定时跑模板，产品没有Agent价值。

**决定：** 周期产品的核心是AttackSurface Snapshot Diff、历史Finding精确复测、变化驱动的计划调整、身份/流程
覆盖和Coverage Ledger。模板扫描只是Signal来源。

### Q17：核心成功指标是什么？

**攻击意见：** 工具数、Agent数、Token数、Star数和演示漏洞都不能说明产品有效。

**决定：** 核心质量指标为唯一且可复现Finding、Precision、覆盖账本完整性、到首个有效Finding的时间、复测
稳定性、人工介入、成本、策略违规和清理成功率。安全违规必须作为独立否决指标，不能被Finding数量抵消。

### Q18：路线是否仍然过长且没有早期产品？

**攻击意见：** R0-R12如果按基础设施顺序串行执行，用户多年看不到可用产品。

**决定：** R1-R2建立共享骨架和多模型协议；Source Hunt 从 R2 后推进 Agent 调查与动态验证，Authorized Red
Team 同期推进 Recon、Browser、身份和攻击链。上线验收与生产巡检在核心能力通过相应安全准入后形成交付闭环，
Hybrid 等待两边协议稳定。

### Q19：四入口是否应共享同一个Prompt和工具集？

**攻击意见：** 共用会扩大上下文和权限，导致模型在生产巡检中选择红队工具。

**决定：** 共用领域协议，不共用完整Prompt或工具集合。Engine、Agent角色和ExecutionProfile共同决定最小工具视图；
Broker再次从可信注册表校验，模型看不到未授权工具。

### Q20：如何避免再次夸大当前进度？

**攻击意见：** 组件测试、真实模型PONG、库级Docker路径和离线报告都曾容易被描述成“Agent可用”。

**决定：** 能力状态统一为designed、offline_tested、isolated_integration_tested、lab_admitted、authorized_pilot、
production_supported。每项对外声明必须链接可复现验收记录。不存在产品入口时不能用底层组件通过代替产品完成。

### Q21：多模型接入是配置功能，还是架构能力？

**攻击意见：** 如果只增加一个 Base URL、模型名和 API Key 表单，实际代码仍可能绑定 CUC 的协议、响应结构和
能力假设；切换默认模型还会破坏长任务复现。

**决定：** 建立 ProviderProfile、CapabilityManifest、ModelRoute 与 FlowModelSnapshot。CUC/DeepSeek 只是首个
Profile。工作区切换影响新 Flow，运行中 Flow 默认固定模型快照；密钥与私有端点只进入受限秘密存储，Worker、
普通日志、Evidence 和模型上下文均不可见。详细设计见 `MODEL-PROVIDER-CONTROL-PLANE.md`。

## 3. 红线判断

以下任一情况出现，产品定位评审视为失败：

- README再次把VulnLoom描述成仅限Python白盒工具；
- README把尚无URL入口的组件集合描述成自主渗透产品已可用；
- 四入口各自实现Scope、Evidence或Finding；
- 生产巡检通过Prompt而不是Policy限制副作用；
- Scanner命中或模型置信度直接生成Finding；
- 红队名称默认开放内网、凭据攻击、持久化或数据外传；
- 为保留旧代码而让新URL主链重复审批、重复状态或无法自主演进；
- 为追求Benchmark得分绕过产品安全边界。

## 4. 保留的开放决策

以下问题依赖产品或部署偏好，不能由本轮自审伪造答案：

- 项目最终许可证；
- Raw Evidence默认保留时间和加密密钥托管；
- 生产默认请求率和允许的验证强度；
- 首个Browser/Proxy技术选型；
- 域名所有权验证是否作为托管版本强制要求；
- 单机版与团队版的商业和发布边界。

这些问题不阻塞R1纯领域模型，但必须在相关外部能力实现前通过ADR决定。

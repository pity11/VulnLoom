# M9.5 minimal ablation experiment

This experiment mutates only the sealed M9.4 observations in memory. It does not execute fixture
code, run Validation, change a production Candidate, invoke Runner/Broker/provider, build a Target,
access a network, approve an action, or create a Submission.

| Variant | Recall | Precision | Trace | Stable violations |
|---|---:|---:|---:|---|
| full | 1.000 | 1.000 | 1.000 | none |
| without Candidate recall | 0.800 | 1.000 | 1.000 | `candidate_recall_below_minimum`, `base_quality_gate_failed`, `framework_mismatch` |
| without cross-file trace | 1.000 | 1.000 | 1.000 | `cross_file_trace_missing` |
| without safe-negative filter | 1.000 | 0.833 | 1.000 | `candidate_precision_below_minimum`, `base_quality_gate_failed`, `negative_candidate_observed` |

The main result is straightforward: Candidate coverage and safe-negative filtering materially control
recall and precision. The coarse M9.3 trace metric only checks whether some trace exists, so truncating
a two-hop path still reports 1.000; M9.4's per-case minimum call-chain check catches that loss. Both
layers are therefore useful, and no additional scoring model is justified by this small experiment.

Reproduce with:

```console
python scripts/run_m9_5_ablation.py
```
